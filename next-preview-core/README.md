# @prismetic/next-preview-core

Hybrid static/preview architecture for Next.js + Strapi projects.

Enables a production build that is a pure static export and a preview build hosted on S3 that fetches live Strapi content directly from the browser on page load — no Node.js server required.

## Installation

```bash
npm install @prismetic/next-preview-core
```

Also requires `@tanstack/react-query` as a peer dependency:

```bash
npm install @tanstack/react-query
```

## Exports

### `PreviewProviders`

Wrap your preview layout in this provider to enable React Query caching. Layout data (Navbar, Footer) fetched once will not refetch on page navigation.

```jsx
// src/app/[locale]/layout.jsx
import { PreviewProviders } from "@prismetic/next-preview-core";

const isPreview = process.env.NEXT_PUBLIC_APP_ENV === "preview";

return isPreview ? (
  <PreviewProviders refetchOnWindowFocus={true}>
    <YourPreviewLayoutFetcher locale={locale}>
      {children}
    </YourPreviewLayoutFetcher>
  </PreviewProviders>
) : (
  // ... static layout
);
```

### Best Practice: `refetchOnWindowFocus`
We highly recommend passing `refetchOnWindowFocus={true}` to `<PreviewProviders>`. 
* **Seamless Editing**: When a content editor updates data in Strapi and tabs back to the Preview website, the current page will automatically and silently refetch the freshest data.
* **Performance Optimized**: The provider intelligently uses `{ refetchType: 'active' }`. It will **only** refetch the page currently visible on the screen, completely ignoring any background cache queries (such as those generated by link-hover prefetching). This eliminates wasteful GraphQL requests.

### `withLivePreview(WrappedComponent, fetcherFn, cacheKeyGenerator, options?)`

A Higher-Order Component that handles `useQuery`, loading/error states, and injects fetched data into your UI component.

| Argument | Type | Description |
|---|---|---|
| `WrappedComponent` | `React.Component` | Your pure UI component |
| `fetcherFn` | `async (props) => data` | Async function that fetches the data |
| `cacheKeyGenerator` | `(props) => string[]` | Returns the React Query cache key array |
| `options` | `{ loading?, notFound?, error? }` | Optional. Custom loading, not-found and error output, [see below](#custom-loading-not-found-and-error-output) |

```jsx
// src/components/preview/PreviewHome.jsx
"use client";

import { withLivePreview } from "@prismetic/next-preview-core";
import HomeUI from "@/app/[locale]/HomeUI";
import { fetchHomepageContent } from "@/api/queryModules";

export const PreviewHome = withLivePreview(
  HomeUI,
  ({ locale }) => fetchHomepageContent(locale),
  ({ locale }) => ["homepage", locale]
);
```

Then in your `page.jsx`:

```jsx
// src/app/[locale]/page.jsx
import { PreviewHome } from "@/components/preview/PreviewHome";

export default async function LocaleHomePage({ params }) {
  const { locale } = await params;
  const isPreview = process.env.NEXT_PUBLIC_APP_ENV === "preview";

  if (isPreview) return <PreviewHome locale={locale} />;

  // Production: fetch data server-side
  const data = await fetchHomepageContent(locale);
  return <HomeUI data={data} />;
}
```

### Custom loading, not-found and error output

The fourth argument replaces the built-in blocks, for example to translate them.

| Option | Shown when | Default text |
|---|---|---|
| `loading` | there is no result yet and a fetch is running | `Loading preview...` |
| `notFound` | the fetcher returned no data (`null`, `undefined` or another falsy value) | `Page not found!` |
| `error` | the fetcher threw and there is no data to show | `Preview failed to load.` |

Each option takes one of these values:

| Value | Output |
|---|---|
| left out | The default block, exactly as in 1.0.16 |
| string or number | The text inside the default block; its markup and style stay. For `error`, the error's message line stays under it |
| any other React node | Replaces the default block entirely |
| `null` | Nothing |
| function | Called on each render with the component's props (`error` also gets the error); its result follows the rows above |

Translated texts that read `locale` from the component's props:

```jsx
const previewTexts = {
  en: { loading: "Loading preview...", notFound: "Page not found!", error: "Preview failed to load." },
  "zh-CN": { loading: "正在加载预览…", notFound: "页面不存在", error: "预览加载失败" },
};

export const PreviewHome = withLivePreview(
  HomeUI,
  ({ locale }) => fetchHomepageContent(locale),
  ({ locale }) => ["homepage", locale],
  {
    loading: ({ locale }) => previewTexts[locale].loading,
    notFound: ({ locale }) => previewTexts[locale].notFound,
    error: ({ locale }) => previewTexts[locale].error,
  }
);
```

To replace a block with your own component, pass an element, for example `{ notFound: <NotFoundPage /> }`.

### Error state

When `fetcherFn` throws (or its promise rejects), the preview shows an error block instead of `Page not found!`.

- Under `PreviewProviders`, React Query retries once first. The loading block stays up until the retry has failed too.
- The default block looks like the not-found block, with the text `Preview failed to load.` When the error is an `Error` with a message, the message is shown underneath in a smaller font.
- Data from an earlier successful fetch wins. If a later refetch fails, the page keeps showing that data.
- Each error is logged once: `console.error("[preview] Fetch failed", queryKey, error)`.

**Limit:** the error block shows only when the fetcher throws. A fetcher that catches the error and returns `null` still gives `Page not found!`.

## Upgrading to 1.1

A site that calls `withLivePreview` with three arguments needs no code change. It gets the same loading, not-found and data output as with 1.0.16, except in two cases:

- **The fetcher throws.** After the retry, the page shows the error block (`Preview failed to load.` and the error's message) instead of `Page not found!`, and logs `[preview] Fetch failed` once.
- **The fetcher resolves `undefined`.** The page still shows `Page not found!`, and React Query no longer logs "Query data cannot be undefined". The empty result is now cached like any other result, for `staleTime` (5 minutes by default): coming back to the page within that time shows `Page not found!` without fetching again. A reload, or a focus refetch with `refetchOnWindowFocus={true}`, still fetches again, so use `refetchOnWindowFocus={true}` for preview, as recommended above.

## Deployment

From the repo root (`prepublishOnly` runs the build):

```bash
npm publish -w next-preview-core
```

## Build Commands

| Command | Output |
|---|---|
| `npm run build` | Production static export (data baked in at build time) |
| `npm run build:preview` | Preview static export (client-side fetch on page load) |

Add to your `package.json`:

```json
{
  "scripts": {
    "build": "next build",
    "build:preview": "NEXT_PUBLIC_APP_ENV=preview next build"
  }
}
```

## Development

```bash
npm test -w next-preview-core        # vitest — 54 tests, plus 5 type tests
npm run build -w next-preview-core   # tsup — CJS, ESM and .d.ts in dist/
```

`src/__fixtures__/withLivePreview-1.0.16.tsx` is the 1.0.16 source, byte for byte; the tests compare the default output against it.

`tsconfig.json` sets `"ignoreDeprecations": "6.0"` because tsup always passes `baseUrl`, which TypeScript 6 rejects without this flag.

## Local Development (npm link)

To test changes to this package in a project before publishing:

```bash
# 1. From the npm-packges repo root
npm run build -w next-preview-core
npm link -w next-preview-core

# 2. In your project directory
npm link @prismetic/next-preview-core
```

A linked package resolves `react` and `@tanstack/react-query` from this repo, which can give a site two copies of React ("Invalid hook call"); to test in a site, prefer `npm pack -w next-preview-core` and install the tarball there.

To unlink:
```bash
npm unlink @prismetic/next-preview-core
```
